# Sealed offline packages («snowden mode»)

Передача зашифрованного контента модулей на десктоп-клиент так, чтобы при просмотре
на диске не оставалось ни одного байта открытого текста: ни файлов, ни превью,
ни кэша. Только оперативка, стриминг с расшифровкой на лету.

Универсальная система: любой модуль может отдавать sealed-пакеты по этим правилам,
десктоп-клиент их принимает по этим же правилам. Конкретика Vault (чья парольная
фраза, какие ресурсы) — в конце, механику делят все.

Статус: системный проект (spec). Реализации пока нет ни на узле, ни на клиенте.

## 0. Модель угроз и обещания

Есть у злоумышленника:

- дамп БД узла, весь трафик, все файлы пакетов на диске клиента, украденный диск —
  видит только шифртекст. Содержимое — задача офлайн-перебора парольной фразы,
  как у запертого Vault сегодня.
- запущенный разблокированный клиент в руках владельца — всё видно, это нормально.

Обещаем:

1. Открытый текст существует только в RAM: ключи, расшифрованные чанки, кадры.
2. На диск не пишется ничего открытого: ни файлы, ни превью/постеры, ни миниатюры,
   ни data:-URL, ни логи с контентом, ни своп по нашей воле (ниже про residual).
3. WebView/рендер не кэширует: ни дисковый, ни memory-кэш после лока.
4. Старый клиент, не знающий sealed, пакет не открывает вообще (fail closed),
   а не «открывает с дырками».

Явно НЕ обещаем (residual, честно в UI не врём):

- RAM-форензика включённой машины, cold boot, hibernation-файл ОС.
- Своп/подкачка ОС: свой `mlock` делаем где можем (ключи), чужой pagefile
  контролировать не можем. Рекомендация: FDE + отключённый hibernate.
- Скриншоты средствами ОС, shoulder surfing.
- Скомпрометированная ОС.

Парольная фраза — весь секрет (без pepper), как у Vault: соль и параметры в открытую,
всё остальное — перебор.

## 1. Термины

- **Sealed-пакет** — офлайн-пакет, чьи data-ресурсы лежат в манифесте и на диске
  только шифртекстом. Признак — объект `sealing` на верхнем уровне манифеста.
- **Package DEK** — случайный 32-байтный ключ пакета (на версию пакета; новый снапшот
  с новым содержимым MAY ротировать DEK, wrapped_dek в манифесте соответственно новый).
- **KEK** — ключ из парольной фразы через Argon2id, живёт только в RAM, только пока
  пакет разблокирован.
- **Resource key** — подключ ресурса, выводится из DEK через HKDF, никогда не хранится.

## 2. Криптография (точная, общая для узла и клиента)

Выбор примитивов — пересечение возможностей сторон:

- Узел (Python `cryptography`): AES-GCM, ChaCha20-Poly1305 (12-байтный nonce, НЕ XChaCha —
  его в `cryptography` нет), HKDF-SHA256, Argon2id.
- Клиент (Rust): `argon2`, `chacha20poly1305` (IETF-вариант с nonce 12 — НЕ XChaCha
  из соседнего `credentials.rs`), `hkdf`, `sha2`, `unicode-normalization` (NFC),
  `zeroize`. Реализация: `netsanctum-desktop/src-tauri/src/sealed/`.

Отсюда фиксируем для sealed-пакетов:

- Шифр: **ChaCha20-Poly1305 IETF, nonce 12 байт**. XChaCha НЕ использовать
  (узел его не умеет, а два разных шифра — два места для ошибки).
- KDF: **Argon2id v1.3, output 32 байта, salt 16 байт, m=65536 KiB, t=3, p=1**.
  `p=1` обязательно: валидаторы с обеих сторон — узел `p ∈ 1..=16`,
  клиент `p ∈ 1..=4`, пересечение диктует единицу (заодно дешевле на мобильных).
  Читатель проверяет параметры ДО аллокации в границах
  `m ∈ 32768..=262144, t ∈ 1..=10, p ∈ 1..=4` и отказывает иначе.
- Парольная фраза: сначала **NFC-нормализация** (совместимость с узлом), затем UTF-8.
- HKDF-SHA256 для подключей (ниже).

### 2.1 Иерархия ключей

```text
passphrase (вводит пользователь, в RAM, zeroize)
  → Argon2id(salt_16, m=65536, t=3, p=1) → KEK_32 (RAM, zeroize)
  → ChaCha20(KEK).open(wrapped_dek, aad=wrap_aad) → DEK_32 (RAM, zeroize)
  → HKDF-SHA256(DEK, salt="ns:sealed-pkg:res:v1"||package_id, info=canonical_url)
      → resource_key_32 (RAM, zeroize, per resource)
```

`wrap_aad = b"ns:sealed-pkg:wrap:v1" || u16be(len(package_id)) || package_id
|| u16be(len(canonical_kdf_json)) || canonical_kdf_json || salt_16`.

`canonical_kdf_json` — JSON с сортировкой ключей и компактными разделителями
(та же канонизация, что `canonical_params` на узле).

`canonical_url` — URL ресурса как в манифесте (включая query).

### 2.2 Малые ресурсы (JSON/HTML-данные — целиком в RAM)

Байты: `nonce(12) || ChaCha20(resource_key, nonce, plaintext, aad)`,
`aad = b"ns:sealed-pkg:res:v1" || u16be(len(url)) || url || u64be(plaintext_len)`.

### 2.3 Большие ресурсы (видео/аудио — чанками, seekable)

Чанк 1 MiB. Байты:

```text
header(33): magic "NSSEAL\x01\x00\x00"(9) || file_nonce(8, random per resource)
          || chunk_size u32be || plaintext_len u64be || chunk_count u32be
chunk[i]:   ChaCha20(resource_key, nonce=file_nonce||u32be(i), chunk_i,
                     aad=chunk_aad||u32be(i))
chunk_aad = magic || 0x00 || file_nonce || url_utf8
          || chunk_size u32be || plaintext_len u64be || chunk_count u32be
```

Заголовок сам по себе НЕ аутентифицирован, но `plaintext_len`, `chunk_size`,
`chunk_count` входят в AAD каждого чанка: подмена заголовка валит тег —
fail closed. Заголовок — недоверенный ввод, длина из него для Content-Length
допустима только потому, что любой чанк мимо неё не расшифруется.

### 2.4 Что открыто, что секретно

Открыто by design (в манифесте, на диске): соль, параметры KDF, `wrapped_dek`,
URL, mime plaintext, число ресурсов. `size`/`sha256` sealed-ресурсы не несут
(см. ниже). Секрет: парольная фраза, KEK, DEK, resource keys, весь plaintext.

`size`/`sha256` в манифесте — по шифртексту. Существующий путь проверки закачки
и CAS на клиенте работает без изменений: хеш сошёлся → байты те самые →
только потом расшифровка.

## 3. Расширение манифеста (совместимость — fail closed)

```json
{
  "schema_version": 1,
  "package_id": "vault_sealed_5",
  "sealing": {
    "version": 1,
    "kdf": {"algorithm": "argon2id", "memory_kib": 65536, "iterations": 3, "parallelism": 1},
    "salt": "base64url(16)",
    "wrapped_dek": "base64url(nonce(12) || ct(48))"
  },
  "resources": [
    {"url": "/api/vault/sealed/5/items?package_id=vault_sealed_5", "type": "sealed",
     "mime": "application/json"},
    {"url": "/api/vault/sealed/media/9?package_id=vault_sealed_5", "type": "sealed",
     "mime": "video/mp4"}
  ]
}
```

Sealed-ресурсы НЕ несут `size`/`sha256`: каждые байты генерируются со свежими
nonce, поэтому хеш манифеста никогда бы не сошёлся. Это документированный
legacy-фолбэк стандарта (байты всегда качаются заново и проверяются
расшифровкой, а не сравнением хеша) — тот же режим, что у динамического NSP.

Правила:

- Поле `sealing` на верхнем уровне = «пакет sealed». Клиент БЕЗ поддержки sealed
  ОБЯЗАН такой пакет не открывать («требуется обновление»), а не открывать
  частично. Клиенты с поддержкой: ресурсы `type: "sealed"` идут только через
  sealed-тракт (п.5).
- `type: "sealed"` — новый тип ресурса. Неизвестные типы старые клиенты и так
  пропускают, но верхнеуровневый `sealing` страхует от «открыть с дырками».
  Реализация на узле: `sealed` в `RESOURCE_TYPES`, hybrid держит sealed
  standalone, в NSP они не пакуются никогда.
- `mime` — mime **plaintext**, нужен шлюзу для Content-Type (из шифртекста не вывести).
- `plain_size` НЕ кладём: длина plaintext недоверенная до расшифровки, шлюз берёт её
  из заголовка чанкового конверта (аутентичность — через теги чанков, fail closed).

## 4. Правила продюсера (любой модуль)

- Снапшот полный, как у обычных пакетов; sealed и plaintext НЕ смешиваются в одном
  пакете: либо пакет sealed целиком (кодshell разрешается открытый только если он
  не несёт данных — на практике sealed-пакеты состоят только из sealed-ресурсов).
- Код (html/css/js) — открыткой можно; данные (json/binary/image/media) — только
  sealed. `data:`-URL внутри sealed JSON запрещены как plaintext: либо отдельный
  sealed-ресурс, либо опустить.
- Никаких превью/постеров/миниатюр в sealed-пакете — ни отдельных, ни
  «для удобства». Рендер отсутствующего постера = пустой кадр, это фича.
- Наружу только алиасы (типа `public_title`): настоящее имя sealed-сущности в
  манифест и URL не попадает.
- Резолвер пакета (`package_prefixes`/`package_resolver` уже generic в реестре)
  для sealed-префиксов валидирует строго: неизвестный id, незапечатанная
  коллекция — ValueError, не пустой список.

## 5. Поведение десктоп-клиента

### 5.1 Закачка

Без изменений относительно обычных пакетов: шифртекст в CAS/standalone-файлы,
проверка транспорта (same-origin, без кросс-кросс-редиректов). `size`/`sha256`
отсутствуют — клиент всегда качает sealed-ресурсы заново (legacy-фолбэк
стандарта) и считает локальный SHA для CAS-адресации. В NSP sealed-ресурсы
не класть (standalone).

### 5.2 Открытие

1. Пользователь выбирает sealed-пакет → нативный (НЕ WebView) промпт парольной
   фразы. Фраза — в zeroize-буфер, ни в JS, ни в логи, ни на диск.
2. Деривация KEK: параметры из манифеста, проверка границ ДО аллокации
   (`m 32768..=262144, t 1..=10, p 1..=4` — те же, что у credential vault).
3. `unwrap_package_dek` → DEK в `Zeroizing<[u8; 32]>`, живёт до лока.
4. Неверная фраза = ошибка аутентификации без различия причин.

### 5.3 Шлюз: расшифровка только в RAM

Новый `Segment::Sealed`: по URL из манифеста — точная строка (включая query) идёт
в HKDF info и AAD; для поиска файла допустима существующая нормализация, для
ключа — нет.

- Малые ресурсы: целиком в RAM, открыть, отдать с `no-store`. Лимит размера
  малого ресурса (напр. 32 МБ) — больше только чанками.
- Медиа/Range: прочитать заголовок (33 байта), проверить UNSEned-размеры,
  расшифровать ТОЛЬКО покрытые чанки, отдать. Полный файл в RAM никогда.
- Временные файлы запрещены конструктивно: в sealed-тракте нет ни одного
  `File::create` для plaintext (ловится canary-тестом, п.7).
- Ответы: `Cache-Control: no-store` (уже есть), Content-Type из `mime` манифеста.

### 5.4 WebView и кэш

- Sealed-контент только через loopback-шлюз с per-unlock capability (кука сессии
  шлюза ротируется при локе — старые URL умирают с 403).
- Видео — через blob:-URL из authorized fetch (паттерн уже есть в вебюи Vault),
  revoke при перерендере и при локе; `src` элементов чистить при локе.
- Ephemeral WebView profile для sealed-сессий там, где API платформы позволяет
  (WKWebView nonPersistent store и аналоги); иначе — `no-store` + revoke как
  базовый уровень. Дисковый HTTP-кэш WebView для sealed-origin должен быть пуст —
  проверяется тестом профиля после прогона.
- Service worker'ы для sealed-origin запрещены; обычный page-cache/bfcache для
  sealed-вью — отключить/обойти навигацией.

### 5.5 Лок

Явный лок + idle-timeout (дефолт 15 минут без обращений к DEK) + смерть процесса:
zeroize DEK и подключей, ротация capability шлюза, revoke blob-URL, увод DOM
со страницы, `sealed_packages` в памяти — забыть. Ключи никогда не persistятся —
это и есть весь механизм «забыть».

### 5.6 Гигиена памяти (честно)

- Rust: `zeroize` для фразы, KEK, DEK, подключей, plaintext-буферов чанков.
- JS: явного zeroize нет — plaintext держим вне JS-строк где возможно (медиа —
  блобы, JSON — увы, парсится; смягчается локом + revoke + отсутствием персистентности).
- `mlock` для DEK — опционально, best-effort (в контейнерах часто запрещён).
  Своп/гибернация ОС — residual, в UI не врём: требуем FDE на устройстве.

## 6. Совместимость

| Сторона | Пакет sealed | Поведение |
|---|---|---|
| Старый клиент | видит `sealing` | отказать («требуется обновление»), НЕ открывать частично |
| Новый клиент | обычный пакет | как раньше |
| Старый узел | новый клиент | sealed-пакетов нет, нечего открывать |
| Новый узел | `vault_all` | без изменений, sealed-ряды исключены как раньше |

## 7. Тесты (обе стороны)

- Golden-векторы: `tests/fixtures/sealed_transfer_vectors.json` — KEK, wrap AAD,
  подключи, малый конверт целиком, заголовок + пробы чанков. Rust читает копию
  того же файла (`netsanctum-desktop/src-tauri/src/sealed/vectors.json`):
  имена полей — кросс-контракт, переименование ломает другую сторону, а копия
  требует ручной синхронизации при смене векторов.
- Отказы: чужая фраза, битый тег, усечение, переписанная длина, чужой URL/package,
  абсурдный KDF, неизвестная версия, диапазон за концом.
- Раунды: пустой/ровный/неровный размеры, stream-writer ↔ stream-reader,
  короткий стрим валит конверт, NFC-эквивалентность.
- Canary «нет plaintext на диске»: положить токен в sealed-контент, прогнать
  закачку+открытие+стриминг, обыскать data_dir — токена быть не должно; заодно
  assert, что в коде sealed-тракта нет записи plaintext-файлов.
- Шлюз: Range по sealed, лок отзывает URL, lock-timeout, no-store на всех ответах.

### Vault: первый sealed-продюсер (реализовано, п.2)

- Пакет на коллекцию: `package_id = vault_sealed_<collection_id>`, фраза = фраза
  коллекции.
- Package DEK детерминирован: `HKDF(inbox_private, salt="ns:sealed-pkg:<id>",
  info="ns:sealed-pkg:dek:v1")` — не хранится, следует за rekey автоматически.
- `wrapped_dek` + соль лежат в колонках `sealed_pkg_salt/sealed_pkg_wrapped`,
  пишутся при создании, при unlock (если пусто) и при rekey. Манифест отдаёт
  stored копию и никогда не оборачивает on demand: у него есть токен сессии,
  а не парольная фраза.
- Эндпоинты (все требуют unlock-токен, 423 если заперт):
  `GET /api/vault/sealed/manifest?collection_id=` (409, если wrap ещё не создан),
  `GET /api/vault/sealed/<id>/items?package_id=` (снимок sealed JSON, после сборки
  rollback — открытые колонки никогда не коммитятся),
  `GET /api/vault/sealed/media/<item_id>?package_id=` (перешифровка file key →
  resource key стримингом, постеры не отдаются никогда).
